# Решение

## Затраченное время

- Настройка окружения: ~5 минут (22:52–22:56). Образ API не собирался:
  Debian 11 снят с поддержки, `deb.debian.org` отвечал 404 на `libpq-dev`.
  В `backend/Dockerfile` добавлена одна строка: apt-источники переключены
  на `archive.debian.org`. Остальное окружение не менялось.
- Разработка, тесты и документация: ~20 минут (22:56–23:15).

## Найденные причины

### 1. При быстром переключении открывается предыдущая заявка

- **Воспроизведение.** С `DEMO_LATENCY=1` карточка 101 отвечает ~1,1 с,
  остальные ~0,1 с. Открыть #101 и сразу другую заявку: через секунду
  карточку перезапишет ответ для 101. Так же ведёт себя ответ сохранения:
  сохранить #101, переключиться, и карточку подменит ответ POST.
- **Причина.** В `TicketPanel.jsx` эффект загрузки не отменял и не отбрасывал
  устаревшие ответы. `save()` после ответа безусловно вызывал
  `setTicket` / `setHistory`.
- **Исправление.** Загрузка отменяется через `AbortController` в cleanup
  эффекта. При переключении карточка, история и сообщения сбрасываются.
  Ответ сохранения применяется к карточке, только если её id совпадает
  с текущим выбранным (`useRef`). Список обновляется всегда. Список в `App`
  защищён счётчиком запросов, применяется только последний ответ.
  Задержки API не убраны.
- **Проверка.** `frontend/src/TicketPanel.test.jsx`: управляемый `fetch`
  отвечает в нужном порядке. Тесты «поздний ответ загрузки…» и «ответ
  сохранения предыдущей заявки…» падали на исходном коде и проходят после
  исправления.

### 2. Карточка заявки без источника падает

- **Воспроизведение.** `GET /api/tickets/103` возвращал 500.
- **Причина.** `TicketRepository::find()` искал источник отдельным запросом
  с `NULL`, получал `false` и обращался к `$source['id']`. Notice
  «array offset on bool» обработчик ошибок превращал в исключение,
  и сервер отвечал 500.
- **Исправление.** Источник читается через `LEFT JOIN`. Если его нет,
  `source: null`. UI показывает «Не указан» в карточке, списке и истории.
- **Проверка.** `test_ticket_without_source` (падал на исходном коде) и
  фронтенд-тест «заявка без источника показывает „Не указан“».

### 3. Сотрудник с правом просмотра изменил источник

- **Воспроизведение.** Войти как viewer, отправить
  `POST /api/tickets/101/source {"source_id": 2}` с CSRF-токеном: ответ 200,
  источник изменён.
- **Причина.** Маршрут проверял только `FUNC_TICKETS_VIEW` и CSRF.
  Право `FUNC_TICKETS_SOURCE_EDIT` проверялось лишь в UI (`canEdit`).
- **Исправление.** `requirePermission($employee, 'FUNC_TICKETS_SOURCE_EDIT')`
  стоит первой проверкой маршрута, до CSRF, чтения тела и обращения к данным.
  Сотрудник и права берутся только из серверной сессии.
- **Проверка.** `test_viewer_cannot_change_source`,
  `test_viewer_cannot_escalate_with_client_fields` (в тело подставлены
  `employee_id` / `permissions` редактора) и
  `test_viewer_forbidden_before_any_other_check`. Все падали на исходном коде.

### Доведение операции до требований

- Порядок для редактора: 404 (нет заявки), затем 403 (архив), затем 400
  (источник). Невалидный JSON тоже проверяется после заявки и архива.
- `source_id` должен быть JSON-integer в диапазоне `1..2147483647`
  и существовать в `sources`. Строки, дроби (включая `2.0`), `null`, `true`,
  массивы, отсутствующее поле и неизвестные id дают 400. Слишком большие id
  в URL дают 404, а не ошибку PostgreSQL «out of range» и 500.
- `UPDATE tickets` и `INSERT ticket_history` выполняются в одной транзакции
  с `SELECT … FOR UPDATE`. При исключении выполняется `ROLLBACK`, и клиент
  получает 500 без деталей.
- Повторный выбор текущего источника возвращает 200 без записи в историю
  и без изменения `updated_at`.
- В `api.js` ответ не в JSON (например, 502 от прокси) превращается
  в понятную ошибку вместо исключения `response.json()`.
- После сохранения обновляются карточка и история (из ответа POST) и список
  (сразу локально, затем перечитывается с сервера).

## Решения и компромиссы

- **Проверки до транзакции и повторно внутри неё.** Маршрут проверяет
  заявку, архив и источник до транзакции, чтобы соблюсти порядок ответов.
  `changeSource()` повторно читает заявку под `FOR UPDATE`, поэтому решение
  опирается на заблокированное состояние. Альтернатива — вся валидация
  внутри транзакции — сделала бы код маршрута менее читаемым.
- **`respond()` внутри репозитория** оставлен, как было в исходном коде.
  Перед ним явно выполняется `ROLLBACK`. Отдельный слой исключений
  предметной области был бы чище, но увеличил бы diff.
- **Одно сохранение за раз во всём UI.** Пока идёт сохранение заявки A,
  кнопка на других карточках тоже заблокирована. Так проще гарантировать
  отсутствие двойной отправки, а ответ всё равно не подменит чужую карточку.
- **Тесты фронтенда** — vitest, jsdom и Testing Library, только
  devDependencies. `fetch` подменён «сервером», которому тест отвечает
  вручную и в нужном порядке. Гонки воспроизводятся детерминированно,
  без таймеров. Браузерный e2e (Playwright) отвергнут: он добавил бы
  загрузку браузеров и нестабильность.
- **API-тесты** написаны на stdlib Python, как `tools/smoke.py`. Они
  проверяют HTTP-поведение, а не наличие строк кода. Перед каждым тестом
  данные сбрасываются через `database/reset.sql`.

## Запуск проверок

```sh
docker compose up --build -d
sh tools/check.sh            # smoke + API-тесты + тесты фронтенда
```

Отдельно:

```sh
python3 tools/test_api.py http://localhost:5173
docker compose exec -T frontend npm test
```

Без учебных задержек:

```sh
docker compose -f compose.yaml -f tools/compose.no-latency.yaml up -d
sh tools/check.sh
```

## Одновременное редактирование

Изменения одной заявки сериализуются через `SELECT … FOR UPDATE`. Второй
запрос ждёт фиксации первого и читает уже новый источник, поэтому история
остаётся непрерывной: `old_source_id` второй записи равен `new_source_id`
первой. Это проверено 20 раундами по два параллельных запроса редакторов,
расхождений нет.

Защиты от потери изменений нет: побеждает последняя запись. Второй сотрудник
не узнает, что его выбор основан на устаревших данных. Его карточка
обновится только после собственного сохранения, а список — после любого
сохранения. Для защиты можно передавать в POST ожидаемый `updated_at`
(или версию) и отвечать 409 при несовпадении.

## Оставшиеся ограничения

- Ручная проверка в браузере не выполнялась: расширение браузера было
  недоступно. Поведение UI покрыто тестами в jsdom, а не реальным браузером.
- Optimistic locking (409) не реализован, см. раздел выше.
- Названия источников в истории берутся из клиентского справочника
  `/api/sources`. До его загрузки история показывает «Не указан».
- API-тесты сбрасывают данные через `docker compose exec db psql`, поэтому
  для запуска без Docker нужно адаптировать команду `PSQL` в
  `tools/test_api.py`.
- Следующие шаги: 409 при конфликте версий, e2e-тест в реальном браузере,
  отдельный HTTP-код ошибки для невалидного JSON у пользователя без права
  (сейчас он получает 403, потому что право проверяется первым — так
  требует ТЗ).
